# 1.3: copy back only what the CPU reads

Roadmap task 1.3, piece **B** (copy-back). Written 26 Nov 2026, after the open-world baseline ([journal](../journal.md)). It gates frames in flight (3.1): lesson 1 of the README says a large copy-back on the critical path makes overlap slower on this machine.

## What it costs today (open world, outside the house)

From the layer's frame lines (`bench/…-world-out-*`):
- **Snapshots:** before each submission, the bytes of every range a shader may write are copied on the CPU (`shadow.rs` `writing`), so that after the submission only the bytes the GPU changed are written back. **408-437 MB a frame**, 93 % of it in copies of 1 MiB or more.
- **Copy-back:** 72 ms and 46 MB a frame (`host.rs` `card_back`, `hand_back`; `shadow.rs` `copy_back_with`).
- Both run on the submitting thread while the card waits: part of the **173-228 ms a frame the card is idle behind us**.

`VICTORY_CARD_BUFFERS_MIN_MB=1` moves some of the comparing to the card, but the frame does not change (491-494 against 491-504 ms).

## The question to answer first

**How much of what is copied back does the title's CPU read before the GPU writes it again?** If it is a small fraction (queries, readback results, a few GPU-driven counters), most snapshots and most copy-back can go: the GPU's copy stays the truth, and title memory is brought up to date only where and when the CPU reads it.

## Measurement: a read census (step 1, behind `VICTORY_BACK_CENSUS=1`)

After a copy-back writes ranges into title memory, put `PAGE_GUARD` on their pages. A guard fault is one-shot: the handler counts the page as read by the title (by range and by the kind of resource), and lets execution continue. At the next submission, report per frame: pages written back, pages the title read, and which ranges.

### Hazards, each with its answer

| Hazard | Answer |
|---|---|
| **Our own reads trip the guards.** The next submission's snapshot (`writing`), refreshes (`copy_mapped`, `crate::fastcopy`) and kernel reads (`ReadProcessMemory`) read the same pages | Before the layer reads a range, it takes its census guards off (a `VirtualProtect` per range, counted). Our own fastcopy handler already restores guards it trips; with the guards gone first, it never sees one. Kernel reads of a guarded page fail under Wine and would read as zeros: the guards must be gone before any. |
| **The write-guard handler (`watch.rs` `on_write`)** protects view memory read-only to see writes | The census guards only private memory at first (`VICTORY_BACK_CENSUS=1`); view memory is left for a second step, and the census reports how much it skips. |
| **The title's own guard pages** | The census guards only pages it wrote back in this submission, which are title buffers the GPU wrote; it records the protection it found and puts it back. |
| **A census guard left on a page the GPU-side copy later refreshes** | Census guards are removed at the next submission in any case; they live for one frame. |
| **Cost** | Counting is a fault per page the title reads (a few thousand a frame at most, by the hypothesis); the switch is off by default. |

## The design that follows if the hypothesis holds (step 2)

- Ranges the title has not read in N frames stop being copied back; their pages get `PAGE_NOACCESS` (or a guard) instead. A fault fetches the range from the GPU copy (a readback that waits for the submission that wrote it), writes it into title memory, and opens the page.
- Their snapshots stop too: a range that is not copied back needs no "before".
- A range read by the title goes back to being copied back eagerly.
- Exact rule (design rule 6): the title never reads a byte older than the GPU's last write. The fault path waits for that write's fence; with frames in flight (3.1), that is the fence of the submission that wrote it.

## Exit

- Open world outside: copy-back under 20 ms and under 10 MB a frame; snapshots under 50 MB a frame.
- The same picture and no device loss in 5 runs of each scene.
- Then 3.1 (frames in flight) on top.
